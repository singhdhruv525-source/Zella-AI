# Zella Voice: instructions for AI agents

Read these before any work, and follow them. They are the project's source of truth:

| # | Document | Use it for |
|---|---|---|
| 1 | `docs/ARCHITECTURE.md` | The required design: every flow, boundary and requirement (`REQ-*`) |
| 2 | `docs/PRODUCT.md` | What Zella Voice is and does, every feature and its honest status |
| 3 | `docs/DESIGN_SYSTEM.md` | Colours, typography, spacing, components; tokens live only in `web/src/styles/tokens.css` |
| 4 | `docs/BACKEND_SCHEMA.md` | Every table, column, policy and function (generated by `docs/generators/backend_schema.py`) |
| 5 | `ZELLA_VOICE_RULES.md` | The rules: the twelve non-negotiables (`NN-1` to `NN-12`), security, privacy, honesty, definition of done |
| 6 | `docs/MEMORY.md` | Where things stand now: what is live, decisions, open problems, lessons learnt |

Cite rule IDs (for example `NN-3`, `ARC-11`) when they shape a decision. When the documents disagree, the rulebook
wins, then the architecture; fix the disagreement in the same pull request.

## Keep them true

Update them in the same pull request as the change:

- **A new or changed feature or page:** update `docs/PRODUCT.md`, and `docs/ARCHITECTURE.md` when the design
  changes (`ARC-11`).
- **A schema change:** regenerate `docs/BACKEND_SCHEMA.md` from an isolated copy of the production schema. Add the
  purpose of any new table in the generator. Update `docs/SCHEMA_STATUS.md` once the migration is applied.
- **A UI change:** follow `docs/DESIGN_SYSTEM.md`, and update it if a token or component changes.
- **Anything that changes what is live, a decision, or a lesson:** update `docs/MEMORY.md`.

## Never, without the owner's explicit approval for that specific action

- Production migrations, deployments, publishing, or live switches (`sms_live`, `email_live`, `calls_live`, ...).
- Real calls, texts, emails or notifications; changes to live voice assistants or phone numbers.
- Billing changes, or destructive actions.

## Never, even with approval

- Never print, commit or ask for secrets, and never copy customer data into fixtures or docs.
- Database tests run only in the isolated test database.
- Never disable tests or weaken authorization to get a pass.
- Never claim what didn't happen, and say which kind of test proved it (local, staging or real provider).
- Never edit an applied migration. Write a new, version-guarded one with an exact rollback in `sql/rollback/`.
- All work goes through a pull request reviewed by CodeRabbit. The owner merges it, or tells Claude to merge it once
  the review is clean and the tests pass (`NN-5`).
- No model IDs in commits, PRs, code or docs.
- The brand is always "Zella Voice", in full.
